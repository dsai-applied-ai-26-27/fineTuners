Writing a course

From the first clone to your work being on the site. In the examples the course is rl; use your own course's short name, the one in its address.

What you work with

The educator kit is a public repository: {{ kit }}{% if kit_version %} (version {{ kit_version.number }}, {{ kit_version.date|date:"j F Y" }}){% endif %}. It holds the instructions your AI assistant follows, the format of every content file, and three small tools. It holds no course.

Your course comes from this site. You download its files, put them into your copy of the kit, add to them, and hand the result back here. Git keeps track of your course on your computer only; nothing you write is ever pushed to the kit's repository.

You need git, uv (it runs the tools and fetches what they need), and an AI assistant that can read and write files on your computer.

Once: set up

  1. Clone the kit and switch pushing off, so that your course can never end up in a public place by accident: 
    git clone {{ kit }}.git
cd dsai-educator-kit
git remote set-url --push origin no-pushing
  2. Download your course. On Educators, under your course, press Download the course files. You get rl.zip: the course exactly as the site has it.
  3. Unpack it into the kit. 
    uv run tools/unpack.py ~/Downloads/rl.zip
    The course is now in courses/rl/, and that state is committed in your copy. That commit is your starting point: from here on, git diff shows exactly what you have added.
  4. Add the material. Put the lecture slides, labs, homework and past papers into courses/rl/source/ (lectures/, labs/, homework/, exams/). Git ignores that folder and the tools never pack it. It belongs to the lecturers and stays on your computer.

Every time: write, check, hand in

  1. Update the kit. git pull brings the latest instructions and format. It never changes your course. You are told on the Educators page, and by e-mail, when there is a new version.
  2. Let your assistant write. Open the kit's folder in it and say: 
    Update the CMS for this course: rl
    It reads AGENTS.md, learns the format from docs/, finds what in source/ is not written up yet, writes it and checks its own work. For one piece at a time: Update the CMS for this course: rl. Only lecture 3. In Claude Code the same thing is /update-cms rl.
  3. Check what it wrote. This part is yours, and it is why the role exists. Read the notes against the slides; work a few cards and one solution by hand. git diff shows every line that is new.
  4. Pack it. 
    uv run tools/pack.py rl
    It checks the course and writes one file, out/rl-<date>-<time>.zip: your course.yaml and content/, nothing from source/.
  5. Hand it in. On Educators, under your course, choose that zip and press Hand in. The site checks it in full. If it passes it is live at once and appears in the list of what was added.
  6. Record it. Your copy and the site now agree, so make that your new starting point: 
    git add -A courses/rl
git commit -m "rl: handed in"

What a hand-in may do

Add. New files, and new lines anywhere in the files that are already there: a new lecture, more cards in a deck, another topic in course.yaml.

Not remove, and not rewrite. Every line the course has on the site must still be in your zip, in the same order. Students' progress is stored under the ids and file names that are live, and nobody's work should disappear because of a slip. If something that is live is wrong, report it with Ask or report and it is changed for you.

Not touch what is the owner's. In course.yaml the topics and the description are yours. Title, code, year and whether the course is open are not.

If the site says the course has changed

Another educator of your course handed something in, or the owner published a change, after you took your copy. Your zip lacks those lines, so it is refused: taking it in would remove them. Put your work on top of the latest version:

git stash                              # set your work aside
# download the course files again, on Educators
uv run tools/unpack.py ~/Downloads/rl.zip   # bring in the site's version
git stash pop                          # put your work back on top
uv run tools/pack.py rl                # check and pack again

Usually git fits the two together by itself. Where both changed the same place it marks the file: both versions are in it between <<<<<<< and >>>>>>>. Keep both sets of lines and delete the markers, or tell your assistant: Resolve the merge conflicts in courses/rl, keeping every line of both sides. Then hand in the new zip.

What never leaves your computer

Anything under source/, and scans, photos or copies of slides and papers anywhere. Write your own summary; draw your own figure. Do not push your copy of the kit anywhere public, and do not fork the kit publicly with your course in it.
